# Инструкции для работы с репозиторием

## Обзор проекта

- Разрабатывай «Зелёный помощник» в рамках КТ №1 НИРС.
- Сохраняй единый Django-проект: HTML-интерфейс и JSON API `/ask`.
- Учитывай, что три ответа подготовлены заранее; BM25 и LLM не подключены.
- Не добавляй RAG, БД, аккаунты или production-развёртывание без задачи.
- Уточняй роли команды и назначение каталогов по [README.md](README.md).

## Требования и порядок изменений

- Перед изменениями прочитай README, `spec/product/` и `spec/tech/`.
- Найди задачи, ответственных и критерии в `spec/tech/tasks.md`.
- До кода обнови затронутое поведение и способ его проверки в спецификации.
- Опиши решение и разбей работу на задачи с ответственными и приёмкой.
- Разделяй реализованное поведение, выполненные проверки и планы.
- Сохраняй чужие изменения; сначала изучи `git status` и текущий diff.
- Не меняй контракт API или демонстрационные данные без обновления спецификации.

## Окружение и запуск

- Используй Python 3.13, Django 5.2 и uv; для инструментов нужен Node.js 24.
- Устанавливай закреплённые зависимости: `uv sync --locked`, `npm ci`.
- Обновляй lock-файлы вместе с изменёнными зависимостями.
- Читай `.env.example`; создай локальный `.env`, не перезаписывая существующий.
- Задай новый `DJANGO_SECRET_KEY`; общего ключа в коде нет.
- Используй `DJANGO_DEBUG=true` для локального интерфейса и static.
- Учитывай приоритет переменных процесса над `.env`.
- Выполняй команды из корня проекта; открывай `http://localhost:8000/`.
- Запускай uv и Compose по очереди: оба используют порт 8000.

```bash
uv run python manage.py runserver
docker compose up --build
docker compose down
```

- Используй `docker-compose.yaml`; в WSL проверь интеграцию Docker Desktop.
- Останавливай созданные для проверки серверы и контейнеры после работы.

## Проверки изменений

- После изменений выполни Django check и все Django-тесты.
- Измеряй весь `app/` со строками и ветвями; порог — минимум 75%, без максимума.

```bash
uv run python manage.py check
uv run python manage.py test tests
uv run coverage run manage.py test tests
uv run coverage report
uv run ruff check .
uv run ruff format --check .
uv run djlint app/assistant/templates --lint
uv run djlint app/assistant/templates --check
npm run lint
npm run format:check
```

- Проверяй UI в браузере по `spec/product/scenarios.md`.
- Подготовь Chromium: `npx --no-install playwright install --with-deps chromium`.
- Выполни `npm run test:browser` против запущенного uv или Compose.
- При изменении запуска проверь оба способа, включая сборку образа.
- В контейнере используй `docker compose exec -T web uv run --no-sync python manage.py check`.
- Запусти там и `python manage.py test tests` через тот же `exec` и uv.
- Запускай benchmark только при изменении реализованного RAG.
- Не считай старые проверки доказательством работоспособности новой версии.

## Стандарты кода

- Пиши содержательные Python docstrings на английском в Google style.
- Добавляй применимые Args, Returns и Raises; не создавай пустые разделы.
- Соблюдай Ruff, длину строки 88 и `.editorconfig`.
- Форматируй Python через Ruff, Django HTML через djLint, JS/CSS через Prettier.
- Проверяй JS через ESLint; используй существующие конфигурации инструментов.
- Сохраняй CSRF, обработку ошибок и безопасный текстовый вывод ответов.
- Не переформатируй корпус, benchmark, LICENSE и генерируемые отчёты.

## Безопасность и ограничения

- Не коммить `.env`, ключи, пароли, окружения, кеши и файлы IDE.
- Сохраняй `.env.example` без реальных секретов; не выводи секреты в логи.
- Не включай секреты в Dockerfile, build args или образ.
- Не добавляй `node_modules/`, отчёты покрытия и Playwright в Git.
- Сохраняй уникальные доказательства КТ №1 и атрибуцию статей корпуса.

## Git и результаты

- Используй префиксы коммитов: feat:, fix:, docs:, style:, test:, chore:, ci:.
- Проверяй `git diff --check` и состав подготовленных к коммиту файлов.
- Объясняй в PR проблему, результат, выполненные проверки и ограничения.
- Обновляй CHANGE_HISTORY: что изменено, команды и их фактический результат.
- Фиксируй проверки UI и ограничения также в `spec/product/kt1.md`.
- Не объявляй невыполненные проверки успешными; указывай блокирующее условие.
- Не публикуй изменения и не отправляй сообщения без отдельного поручения.
- Отличай локальную проверку CI от фактического запуска GitHub Actions.

- Считай пустые строки и блоки кода; символы — Unicode, включая пробелы и LF.
- Пересчитывай объём после форматирования и каждого изменения AGENTS.md.
