# Сценарии

## Основной сценарий RAG (КТ №2)

1. Пользователь открывает `/`. Видит поле «Ваш вопрос», кнопку «Спросить» и три примера вопросов. Примеры — только подсказки: клик заполняет поле, но ничего не отправляет. Подписи о демонстрационной версии нет.
2. Вводит любой вопрос и нажимает «Спросить» (или Enter). Отправляется один `POST /ask` с JSON `{"question": ...}` и CSRF-токеном.
3. Пока идёт запрос: прошлый результат скрыт, кнопка и повторная отправка заблокированы, поле сохраняется, статус «Ищем в статьях и готовим ответ…». Через 8 секунд статус меняется на «Ответ готовится дольше обычного, подождите…». Через 90 секунд запрос прерывается с сообщением о таймауте.
4. Сервер ищет фрагменты BM25 и просит LLM ответить по ним. Ответ — `{answer, sources, refused}`.
5. Если `refused: false`: блок «Ответ» и блок «Источники». Каждый источник — номер и название статьи, фрагмент, ссылка (только HTTP/HTTPS, новая вкладка, `noopener noreferrer`).
6. Если `refused: true`: отдельный блок «Ответа в документах нет» с текстом «В документах нет этой информации»; блоков «Ответ» и «Источники» нет.
7. Новый вопрос заменяет любое прежнее состояние.

## Ошибки и ввод

- Пустой вопрос и пробелы не отправляются; пользователь видит просьбу ввести вопрос.
- HTTP 502 (LLM отклонил запрос или вернул некорректный ответ) и 503 (LLM не настроен или недоступен) показывают текст `error` сервера; если его нет — понятное сообщение по умолчанию. Остальные HTTP-ошибки, ошибка сети, таймаут, не-JSON и ответ без `answer`, булева `refused` или с неверными источниками — сообщение об ошибке.
- При любой ошибке результатов нет, кнопка снова доступна, введённый вопрос остаётся для повторной попытки.
- Ответы и фрагменты выводятся как текст, HTML не исполняется.
- Формой можно пользоваться с клавиатуры. Состояние объявляется через live-region. На ширине 375 и 1280 px нет горизонтальной прокрутки.

## Проверка

- Автоматически: Playwright (`tests/browser/rag.spec.cjs`) подменяет ответ `/ask` на `{answer, sources, refused}`, ошибки 403/502/503, некорректные тела и долгий ответ; один сценарий проходит реальный `/ask` с HTTP-заглушкой LLM.
- Вручную: основной сценарий на 15 вопросах benchmark с реальной LLM, независимая проверка разметки Accuracy и скриншоты — в [КТ №2](kt2.md).
- Сценарии КТ №1 (три подготовленных ответа) заменены этим поведением; их результаты сохранены в [КТ №1](kt1.md) как история.

## Проверки после улучшения качества проекта

Перед запуском подготовить локальный .env с новым ключом и DEBUG=true либо передать настройки средой. Браузерные проверки выполняются Playwright Test из закреплённых Node-зависимостей. Решение и приёмка этих проверок — [quality.md](../tech/quality.md).
