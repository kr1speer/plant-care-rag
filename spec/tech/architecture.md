# Архитектура

## Согласованное решение КТ №1

```text
GET / → Django-шаблон + статические CSS/JS + CSRF-cookie
Браузер → POST /ask → валидация → демонстрационный сервис
        ← JSON: answer, sources ← подготовленный пример
```

Python 3.13, Django 5.2, uv и uv.lock. Секретный ключ обязателен в среде или .env; подготовка описана в README. UI и API — один origin и один процесс Django; отдельного сервера фронтенда нет. Приложение не использует БД, ключи LLM или внешние запросы при ответе.

Расположение: `app/config/` — настройки и маршруты; `app/assistant/` — views, сервис, демонстрационные данные, шаблоны и namespaced static `assistant/`. `data/corpus/` — 28 статей; `benchmark/questions.jsonl` — вопросы будущего benchmark. Каталоги уже содержат материалы, а не только `.gitkeep`.

Демонстрационные примеры хранятся на сервере в одном месте. Шаблон берёт оттуда вопросы; JS не дублирует ответы. Для каждого примера сохраняются имя файла корпуса и публичные поля источника. Сервис не читает корпус при запросе; тест сверяет подготовленные фрагменты и ссылки с файлами корпуса. Docker включает корпус для этого теста.

План и задачи: [tasks.md](tasks.md). Подтверждение реализации и ограничения: [приёмка КТ №1](../product/kt1.md).

## Контракт API

- `GET /` → HTTP 200, HTML интерфейса и CSRF-cookie. Другие методы страницы → 405 (CSRF middleware может отклонить небезопасный запрос без токена раньше).
- `POST /ask` без завершающего слеша; `Content-Type: application/json`.
- Тело — объект с непустой строкой `question` после trim. Дополнительные поля игнорируются.
- Поддерживаемые вопросы и нормализация описаны в [сценариях](../product/scenarios.md).

Пример запроса:

```json
{ "question": "Почему у монстеры мелкие листья без прорезей?" }
```

Ответ HTTP 200: `{"answer": "...", "sources": [{"title": "...", "fragment": "...", "url": "https://..."}]}`. Внутреннее имя файла корпуса в API не передаётся. Для неподдерживаемого вопроса — сообщение об ограничении демонстрации и пустые источники. Постоянная тестовая заглушка заменяется тремя примерами.

Ошибки: строковое поле `error`; 400 — JSON, тип тела или вопрос; 415 — Content-Type; 405 — метод (`Allow: POST`); 403 — CSRF. Неизвестный путь, включая `/ask/`, — 404.

CSRF сохраняется: открыть `/` или выполнить `GET /ask` (405 с cookie), затем отправить POST с cookie и `X-CSRFToken`. Шаблон также содержит CSRF-токен формы. HTML-ответ никогда не подставляется как текст ответа помощника.

## Целевая архитектура RAG (не реализована на КТ №1)

Вопрос → BM25 → контекст → LLM → ответ + источники. Если релевантных фрагментов нет, ответ формирует приложение без вызова LLM. Подробности проектируемого решения — [rag.md](rag.md).

## Запуск и проверка

Оба способа из README открывают интерфейс на `http://localhost:8000/`. Это локальная разработка: DEBUG=true в примере .env, runserver, публикация Compose только на loopback. Развёртывание в интернете — отдельный этап.

Проверки: `uv run python manage.py check`, `uv run python manage.py test tests`; синтаксис JS; браузерные сценарии при uv и Compose; `docker compose config --quiet`, сборка и тесты контейнера; Git diff и проверка свежего checkout. Benchmark RAG здесь не запускается, так как поиска и генерации нет.

## Уточнение конфигурации и проверок качества

Согласованное изменение запуска: обязательный DJANGO_SECRET_KEY из среды или локального .env, DJANGO_DEBUG и DJANGO_ALLOWED_HOSTS из среды, файл docker-compose.yaml. Перед запуском требуется подготовка .env по шаблону либо передача переменных процессу. Подробный контракт, тесты, инструменты и CI описаны в [quality.md](quality.md); результаты подтверждаются отдельно в приёмке.
