# RAG: корпус, поиск и benchmark

Документ описывает корпус, разбиение на фрагменты, собственный поиск BM25 и проверку качества. Ответственный: Антон. Задачи и статусы — [КТ №2 в tasks.md](tasks.md#кт-2-поиск-bm25-и-benchmark).

**Статус КТ №2, часть 1:** корпус из 30 документов, функция `retrieve()` в `app/rag/` и `benchmark/run.py` реализованы в ветке `issue-12`; результаты — в разделе «Результаты». В №13 поиск подключён к API вместе с LLM и отказом, см. [архитектуру](architecture.md). Итоговый интерфейс относится к №14.

## 1. Путь запроса

Реализовано в этой части — первые три шага; остальное — план.

```text
вопрос пользователя
  → токенизация вопроса                         (app/rag, реализуется)
  → BM25 по фрагментам корпуса, лучший фрагмент на документ, top-3
  → результат retrieve(): документ, раздел, фрагмент, ссылка, балл
  → промпт LLM: инструкция + фрагменты + вопрос  (план, Валентин)
  → ответ или отказ «В документах нет этой информации» + источники
```

## 3. Формат файла

Один документ — один файл `data/corpus/NN_slug.md`:

```markdown
# Название статьи

Источник: <URL статьи>
Версия статьи: <revision id Википедии>
Лицензия: CC BY-SA 4.0 ... Текст сокращён: ...

---

Вступление статьи...

## Раздел

Текст раздела...
```

Всё выше первой строки `---` — метаданные: в индекс не попадают, `title` и `url` берутся из реестра. Ниже — текст для поиска.

## 4. Токенизация

Реализация — `app/rag/text.py`, только собственный код и `snowballstemmer`:

1. Нижний регистр, `ё` → `е`, удаление знака ударения U+0301 (в корпусе «Монсте́ра» иначе распалась бы на два слова).
2. Слова — совпадения регулярного выражения `\w+`.
3. Удаление русских стоп-слов собственного списка (предлоги, союзы, частицы, местоимения и вопросительные слова «как», «почему», «какой», «когда»…).
4. Стемминг `snowballstemmer` (русский), чтобы «листья» и «листьев», «клещ» и «клеща» совпадали.

Стоп-слова и стемминг отключаются параметрами — так проверяется пример из лекции. Известное ограничение стеммера: «полив» → «пол», «поливать» → «полива».

## 5. Фрагменты

Реализация — `app/rag/corpus.py`:

1. Текст ниже `---` делится по строкам, начинающимся с `## ` или `### `. Каждый такой раздел — фрагмент; текст до первого заголовка — фрагмент с разделом «Вступление». Заголовки `####` и строки-подзаголовки без `#` остаются внутри фрагмента.
2. Разделы без текста (например, пустой «Культивирование» в D17) фрагментами не становятся.
3. Длинные разделы на КТ №2 не режутся по абзацам: длину учитывает нормализация BM25 (`b`). Деление на куски — возможное улучшение, если benchmark покажет проблему.
4. Индексируемый текст фрагмента — `«<название статьи>. <раздел>.»` + текст раздела. Префикс помогает вопросу «как поливать фиалку» найти раздел именно статьи о сенполии. В результате `fragment` — текст раздела без префикса, название и раздел — отдельные поля.

## 6. Индекс и BM25

Реализация — `app/rag/bm25.py`, без `rank_bm25` и других поисковых библиотек.

- **Обратный индекс:** слово → `{номер фрагмента: tf}`; длина фрагмента `dl` — число его токенов после токенизации; `avgdl` — средняя длина; `N` — число фрагментов.
- **IDF:** `idf(t) = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))`, всегда положителен.
- **Балл фрагмента:** `Σ idf(t) · tf · (k1 + 1) / (tf + k1 · (1 − b + b · dl / avgdl))` по уникальным словам вопроса, `k1 = 1.2`, `b = 0.75`. Повтор слова в вопросе не увеличивает балл.
- **Документ:** балл документа — балл его лучшего фрагмента; при равенстве внутри документа берётся более ранний фрагмент.
- **Порядок:** по убыванию балла, при равенстве — по `doc_id` по возрастанию. Учитываются только фрагменты, где есть хотя бы одно слово вопроса.
- **Индекс** строится один раз при первом вызове `retrieve()` и переиспользуется в процессе.

Проверочный пример из лекции (без стемминга и стоп-слов): A «Возврат оплаты на карту», B «Статус оплаты в приложении», C «Возврат билета через кассу», вопрос «Как происходит возврат оплаты?» → A 0.940, B 0.470, C 0.470; при `k = 2` — A, B.

## 7. Контракт `retrieve()`

```python
from app.rag import retrieve

retrieve(question: str, k: int = 3) -> list[dict]
```

Каждый элемент: `{"doc_id": "D27", "title": "Хлороз растений", "section": "Причины заболевания", "fragment": "...", "url": "https://...", "score": 7.1234}`. Не более `k` элементов, один на документ, порядок из §6.

- Пустой список, если у вопроса нет токенов или ни один фрагмент не совпал.
- `k < 1` — `ValueError`.
- Ошибка реестра (повтор ID, отсутствующий файл, расхождение заголовка или URL с файлом) — `ValueError` при построении индекса.
- Модуль не зависит от Django и не обращается к сети.

## 8. Промпт для LLM (№13, Валентин)

Системное сообщение просит отвечать по-русски только по переданным сведениям и ссылаться на использованные документы. Пользовательское сообщение содержит вопрос и до трёх блоков контекста в формате `[D02] Название — раздел: фрагмент`. Модель возвращает JSON с полями `answer`, `refused` и `sources` (массив ID). Если сведений недостаточно, модель сообщает об этом и возвращает пустой массив источников. Сервис проверяет ID и берёт метаданные источников из результатов поиска.

Ожидаемый для benchmark контракт сервиса: `answer_question(question) -> {"answer": str, "sources": list, "refused": bool}` в `app/assistant/services.py`. Сервис использует тот же контракт в API.

## 9. Benchmark

### Формат вопросов

`benchmark/questions.jsonl`, по одному объекту JSON на строку:

| Поле              | Описание                                                                            |
| ----------------- | ----------------------------------------------------------------------------------- |
| `id`              | `Q01`…`Q15`                                                                         |
| `question`        | Вопрос так, как его задал бы пользователь                                           |
| `relevant_ids`    | ID документов, текст которых отвечает на вопрос; у ловушки — `[]`                   |
| `expected_answer` | Эталон, сверенный с текстом корпуса; у ловушки — «В документах нет этой информации» |
| `type`            | `regular` или `trap`                                                                |

Состав: **10 обычных** вопросов на разные темы (у каждого не меньше 3 релевантных документов) и **5 ловушек** по теме растений, ответа на которые в корпусе нет. Документ считается релевантным, только если его текст отвечает на вопрос или на его часть; упоминание темы вскользь не считается. Цитаты из каждого релевантного документа, подтверждающие эталоны, хранятся в `benchmark/evidence.md`; тест сверяет их с текстом корпуса.

### Метрики

Глубина `k = 3`.

1. **Recall@3** — среднее по 10 обычным вопросам `|relevant_ids ∩ top-3| / |relevant_ids|`.
2. **MRR@3** — среднее по 10 обычным вопросам `1 / ранг` первого релевантного документа в top-3, иначе 0.
3. **Accuracy** — доля обычных вопросов с ручной оценкой `verdict = "correct"` (полностью правильный ответ) из 10. Считается, только когда размечены все 10; иначе `null` и число размеченных.
4. **Correct Rejection Rate** — доля ловушек с `refused = true` из 5; ловушка с ошибкой LLM — не отказ. Без `answer_question` — `null`. Ловушки в Recall@3 и MRR@3 не входят.

### Запуск

Из корня проекта:

```bash
uv run python benchmark/run.py --retrieval-only   # только поиск: Recall@3, MRR@3
uv run python benchmark/run.py                    # поиск + answer_question, если формат совместим
uv run python benchmark/run.py --score benchmark/results/<файл>.json   # пересчёт после разметки
```

Без `--retrieval-only` скрипт импортирует `answer_question` и делает пробный вызов на Q01; его результат сохраняется как ответ Q01, повторного вызова нет.

- Если импорт, настройки LLM (`LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL`), пробный вызов или формат ответа не прошли, прогон **останавливается** с кодом выхода 3 и причиной (имя исключения и сообщение сервиса, без ключа); файл результатов не создаётся. Молчаливого перехода в `retrieval-only` нет — этот режим включается только флагом.
- Если на другом вопросе `answer_question` бросает `LLMError` или `LLMUnavailable`, прогон продолжается: `answer` и `refused` остаются `null`, в поле `error` записываются класс и сообщение ошибки. Сводка показывает число ошибок. Ловушка с ошибкой не считается корректным отказом; обычный вопрос с ошибкой размечается `incorrect`.
- Ответ другого формата на любом вопросе — нарушение контракта: прогон завершается `ValueError`.
- `temperature` в запросе к модели не задаётся (используется значение провайдера), поэтому повторный полный прогон может дать другие ответы; сравнивать имеет смысл файлы результатов, а не только метрики.

### Хранение результатов

`benchmark/results/<YYYY-MM-DD>.json`; если файл за дату уже есть, создаётся `<дата>-2.json`, `-3`… — ручная разметка не перезаписывается. Файлы коммитятся в Git. Содержимое:

```json
{
  "created_at": "2026-11-17T12:00:00+00:00",
  "git_sha": "<HEAD при прогоне>",
  "mode": "full",
  "mode_reason": "",
  "model": "<LLM_MODEL>",
  "base_url": "<LLM_BASE_URL без ключа>",
  "k": 3,
  "bm25": { "k1": 1.2, "b": 0.75 },
  "questions": [
    {
      "id": "Q01",
      "type": "regular",
      "question": "...",
      "relevant_ids": ["D03", "D11", "D14"],
      "expected_answer": "...",
      "retrieved": [{ "doc_id": "D11", "score": 8.1234 }],
      "answer": "...",
      "sources": ["D11"],
      "refused": false,
      "error": null,
      "verdict": null
    }
  ],
  "metrics": {
    "recall_at_3": 0.0,
    "mrr_at_3": 0.0,
    "accuracy": null,
    "accuracy_labeled": 0,
    "correct_rejection_rate": null,
    "errors": 0
  }
}
```

`sources` — ID документов, которые сервис вернул как подтверждение ответа. В режиме `retrieval-only` `model`, `base_url`, `answer`, `sources` и `refused` равны `null`. `verdict` заполняется вручную: `"correct"`, `"partial"` или `"incorrect"`; для итоговой Accuracy КТ №2 используются только `correct` и `incorrect` — догадка или выдуманный факт считается ошибкой. `--score` проверяет значения, пересчитывает `metrics` в том же файле и печатает сводку. Сводка содержит метрики и обычные вопросы, у которых релевантный документ не попал в top-3.

## Результаты

### Полный прогон с LLM — не выполнен

Ожидает настроек `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL`: на машине исполнителя 2026-11-20 их нет ни в `.env`, ни в окружении. `uv run python benchmark/run.py` останавливается с кодом 3: «пробный вызов на Q01 не прошёл … LLMUnavailable». Accuracy, Correct Rejection Rate и разбор ответов появятся после прогона; модель, SHA и файл результатов будут записаны здесь.

### 2026-11-20, `--retrieval-only` — базовая строка для полного прогона

Файл [`benchmark/results/2026-11-20.json`](../../benchmark/results/2026-11-20.json), SHA `a0f72fd`, `k = 3`, `k1 = 1.2`, `b = 0.75`. Recall@3 = 0,500, MRR@3 = 0,883. Выдача top-3 по всем 15 вопросам совпадает с прогоном 2026-11-17 ниже, поэтому разбор промахов поиска остаётся в силе. Опорные документы Q04 перепроверены: D16 и D20 корпус прямо называет суккулентами, `relevant_ids` не менялись; D08 не добавлен, так как корпус не относит его к суккулентам.

### 2026-11-17, `--retrieval-only`

Файл `benchmark/results/2026-11-17.json`; 30 документов, 131 фрагмент, `avgdl` 80,2 токена; `k1 = 1.2`, `b = 0.75`, `k = 3`. Прогон в контейнере дал те же значения.

Полностью найден только Q02. Наблюдаемые причины промахов (параметры под benchmark не подбирались):

- Snowball не сводит однокоренные слова разных частей речи: «желтеют» / «пожелтение», «пересаживать» / «пересадку», «подкармливать» / «подкормки», «загнили» / «подгниваний». Поэтому D27, D29 (Q01), D05, D10 (Q06) и D30 (Q09) не совпадают с вопросом по главному слову.
- Длинные фрагменты, например «Агротехника» D11 (334 токена), набирают балл за частые общие слова («полив», «вода») и вытесняют короткие точные ответы (Q04, Q05).
- Общие слова вопроса («комнатные растения», «опасны») поднимают D23 и D05 в Q08 и Q10, хотя ответ в других документах.

Возможные улучшения для следующих итераций: лемматизация или словарь синонимов, деление длинных разделов, проверка на benchmark каждого изменения.
