# Качество, конфигурация и CI: согласованное решение КТ №1

**Статус:** реализовано и проверено локально; workflow ожидает первого запуска на GitHub. Результаты — в приёмке.

Поведение трёх демонстрационных ответов и API сохраняется. Это улучшение сопровождаемости первой контрольной точки, без реализации RAG. Задачи Q1–Q6 — в [tasks.md](tasks.md).

## Стиль и инструменты

Python 3.13: Ruff (E4/E7/E9, F, I, D, UP, B; Google docstrings; 88 символов), Ruff format, coverage.py, djLint для Django-шаблонов — dev-группа uv и uv.lock. Содержательные английские docstrings модулей, публичных классов/функций/методов: summary и применимые Args/Returns/Raises; без пустых разделов. Не отключать D глобально.

Node 24: ESLint flat config (браузер и Node), Prettier, Playwright Test — private package.json и package-lock.json. ESLint отвечает за JS, Prettier — JS/CSS/JSON/YAML/Markdown, djLint — HTML Django. Форматирование не затрагивает корпус, benchmark, LICENSE и генерируемые артефакты. CI проверяет формат, а не переписывает файлы. Настройки редактора: UTF-8, LF, завершающая новая строка, единые отступы.

Покрытие: весь app/, строки и ветви, включая настройки и ASGI/WSGI. Минимум 75%, верхней границы нет. Тесты не включаются в знаменатель. Результаты — терминал, XML и HTML. Браузерные тесты не смешиваются с Python-метрикой. Предварительный замер до правок: 91% и 18 Django-тестов.

## Конфигурация процесса

- python-dotenv читает корневой .env с override=False; среда процесса имеет приоритет. Отсутствие .env допустимо, если настройки уже заданы средой.
- DJANGO_SECRET_KEY обязателен и непуст после strip; отсутствие/пустое значение — ImproperlyConfigured с именем переменной, без вывода значения. Ключа по умолчанию нет.
- DJANGO_DEBUG: true/false без учёта регистра и с удалением пробелов; по умолчанию false. Другие значения — понятная ошибка конфигурации.
- DJANGO_ALLOWED_HOSTS: CSV с удалением пробелов и пустых элементов, по умолчанию localhost,127.0.0.1,[::1].
- .env.example содержит пустой ключ и несекретные настройки локальной демонстрации (DEBUG=true). .env игнорируется; шаблон отслеживается. Новые LLM/БД-секреты не выдумываются.
- Единственный Compose-файл — docker-compose.yaml. Он явно передаёт настройки через environment и отклоняет отсутствующий/пустой ключ при интерполяции. Ключ не используется при сборке образа.
- Docker остаётся локальным runserver. При DEBUG=false отдача static через runserver не обещается; production-развёртывание вне объёма.

## Браузер и CI

Playwright Test заменяет монолитный browser.cjs: отдельные тесты, новый browser context на сценарий, Chromium, общие timeout/baseURL и trace/screenshot при неуспехе. Сохраняются ответы/источники, нормализация, ошибки подбора, пустой ввод, повторная отправка, очистка источников, HTTP/сеть/некорректный JSON/контракт, восстановление, безопасный текст/ссылки, клавиатура и ширины 375/1280.

GitHub Actions: pull_request в main, push в main, workflow_dispatch. Ubuntu; quality и Python-тесты, затем Docker build/Compose и Playwright против контейнера. Временный случайный ключ задания (не GitHub secret и не личный .env), DEBUG=true для UI. Установка по lock-файлам. permissions contents:read, timeout и concurrency для отмены устаревших запусков. Actions закрепляются полными SHA. Образ не публикуется.

Готовность сервера проверяется HTTP с ограничением времени, не sleep. Отчёты coverage, логи контейнера, trace и скриншоты сохраняются как артефакты; cleanup контейнера выполняется всегда. Workflow считается подтверждённым на GitHub только после фактического remote run, а не после локальных проверок.

## Проверка решения

1. Тесты настроек до реализации: обязательный/пустой ключ, отсутствие dotenv, приоритет среды, DEBUG, CSV-хосты. Изолировать личный .env.
2. Все проверки стиля в check-режиме; повторное форматирование не меняет файлы.
3. Django check и test tests, coverage report >=75%; XML/HTML.
4. Свежая копия: подготовка .env по README, uv и Compose, реальные Playwright-тесты против обоих способов.
5. Проверка ignore-правил, исключения .env из Git и контекста образа; ключа нет в Dockerfile/build args.
6. Сравнение скриншотов и удаление только точных дублей; проверка ссылок и Git diff.
7. Фактические результаты — [приёмка](../product/kt1.md) и CHANGE_HISTORY. Публикация и личный запуск команды — отдельно.
